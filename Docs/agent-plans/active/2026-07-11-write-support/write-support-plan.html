Write support — implementation plan

Generated: 2026-07-11

Source: Docs/agent-plans/active/2026-07-11-write-support/write-support.html

SwiftFITS is today a read-only library: it parses FITS files into a three-level reference-type model (FITSFile → FITSSection → FITSBlock), retains every original 2880-byte block, and round-trips files byte-for-byte via FITSFile.data. There is no card renderer, no mutation API, and no writer. This plan adds full write and serialization support in three sequenced stages that build on one another: first a serialization foundation that renders the existing model back to standards-compliant bytes (formalizing what the round-trip proves), then construction from scratch, and finally in-place modification of parsed files. The design mutates the existing classes (rather than introducing parallel builder types), preserves untouched sections byte-for-byte through dirty-tracking, and adds a symmetric FITSSerializationOptions type with on-write validation that mirrors the existing FITSParsingOptions idiom.

Questions & answers

How should the write API expose mutation, given the model is currently fully closed (private setters, private blocks)?
Mutate the existing classes — open up FITSFile/FITSSection/FITSProperty with mutation methods and re-render cards on write. Keep one model for both read and write rather than introducing parallel builder types.
The parser retains original bytes so unmodified files round-trip byte-for-byte. How should the writer treat that fidelity?
Preserve untouched, re-render touched — keep the retained raw blocks for sections that were not modified (byte-exact), and only re-render cards/blocks for sections that changed. This requires per-section dirty-tracking.
Should the writer have a symmetric options type mirroring FITSParsingOptions, and validate output against the FITS 4.0 standard on write?
Yes — add a FITSSerializationOptions (strict/lenient) type and validate mandatory keywords, BITPIX/NAXIS geometry, and data size before emitting bytes.
The backlog item bundles three capabilities. Should this plan cover all three, and in what order?
All three, in order: serialize an existing parsed file → create from scratch → modify parsed files. The serialization foundation comes first because construction and modification both depend on it.

Notes

Key files (all under SwiftFITS/):

  • FITSFile.swift — top-level class; owns sections, the data round-trip serializer, mandatory-keyword and data-size validation (validateMandatoryKeywords, expectedDataSize), and constants blockSize = 2880, maxDataSize.
  • FITSSection.swift — the HDU/data-unit model; holds private blocks (retained raw bytes), parsed properties, an isFinalized lock, geometry accessors (bitpix, naxis), and the appendData(to:) serialization primitive.
  • FITSBlock.swift — the 2880-byte block wrapper; holds raw data and lazy structural flags (hasEndMarker, hasExtensionMarker).
  • FITSProperty.swift — the 80-byte card parser: keyword, = indicator, quoted strings with '' escaping, comments, and CONTINUE/HISTORY/COMMENT merging. The writer's card renderer is the inverse of this file.
  • FITSValue.swift — public enum with cases logical, integer, float, string, undefined, unknown. The value renderer is the inverse of its parser.
  • FITSParsingOptions.swift — OptionSet template for the new FITSSerializationOptions.
  • FITSError.swift — single error enum; the writer adds serialization/encoding cases here.

Design anchors & conventions to honor:

  • Dirty-tracking is the linchpin of "preserve untouched, re-render touched." Each FITSSection needs a flag (e.g. needsSerialization) set whenever its properties or data mutate; its data/appendData(to:) returns retained blocks when clean and re-renders when dirty. Note the existing isFinalized lock must be reconciled with mutability.
  • Magic numbers to centralize: card size 80 and keyword length 8 are currently hardcoded literals (in FITSProperty, FITSSection.readAndMergeProperties, FITSBlock.hasEndMarker). Introduce named constants and use them on both read and write paths.
  • Fixed- vs free-format: FITS mandates fixed-format for mandatory keywords (value right-justified in columns 11–30, logical in column 30). The renderer must reproduce this; verify against the vendored Documentation/FITS Standard 4.0.pdf.
  • Byte fidelity reference: the existing test allTestFilesRoundTrip (SwiftFITSTests/FITSFile.swift) asserts file.data == data across all fixtures — it must keep passing after every milestone, since the clean-section path is unchanged.
  • Card-formatting reference: TestUtilities (SwiftFITSTests/TestUtilities.swift) already renders keyword records to 80-char/2880-byte blocks in test code — a working reference the library writer should formalize (and the test helpers may later delegate to it).
  • Testing: the project uses swift-testing (import Testing, @Test, #expect), not XCTest. Mirror source files with test files under SwiftFITSTests/.
  • Xcode ⇄ Package sync: an .xcodeproj exists alongside Package.swift — every new source/test file must be added to the Xcode project too, and tests should be run via xcodebuild.
  • Access & style: explicit public on the API surface, internal for cross-type helpers; one primary type per file; let over var; no force-unwrap; doc-comment every declaration (including private); the project's spaced-bracket style (self[ "BITPIX" ]).
  • Open question deferred to M2/M3: exact float formatting (precision, exponent form) that both satisfies the standard and preserves byte-identity for values that originated as text — settle empirically against fixtures during those milestones.

M2 Render FITSValue to a card literal Completed

Completed: 2026-07-11

Goal
Implement the inverse of the value parser: turn a FITSValue into its FITS card-literal text, the smallest unit the writer needs.
Tasks
  • Add a rendering API on FITSValue (e.g. func serialized(...) -> String) covering every case: logical → T/F, integer, float, string (quoted, '' escaping, ≥8-char minimum padding rule), undefined (empty), unknown (verbatim).
  • Decide and document the float formatting policy (precision, exponent form) against the FITS 4.0 standard; verify it against real fixture values.
  • Support fixed-format placement inputs the caller (M3) needs (right-justified vs free-format), or expose enough for M3 to position the literal.
  • Unit tests in SwiftFITSTests/FITSValue.swift: round-trip each case parse→render→parse; assert byte-identity for values that originated as text where feasible.
Implementation notes

Implemented with TDD (red → green). Added public func serialized() throws -> String to FITSValue, plus two private static helpers (serializedFloat, serializedString). No new files, so no Xcode-project changes.

Grounded in the FITS 4.0 standard (vendored PDF §4.2): read the string, logical, integer and real-number format rules directly rather than from memory before implementing.

Two design decisions were surfaced to the user and approved before coding:

  • String padding — minimal literal, no min-8 in M2. The plan's "≥8-char minimum padding rule" predates FITS 4.0 §4.2.1, which removed that requirement except for the XTENSION value. So serialized() emits the minimal free-format literal ('M42'), single-quoted with interior quotes doubled; the null string renders '' and the empty string ' ' (these fall out naturally from the escaping — no special-casing needed). All column placement, right-justification, and the keyword-aware XTENSION min-8 padding are deferred to M3.
  • Float — shortest round-trippable. Uses Double.description (the shortest decimal that parses back to the same Double) with the exponent letter upper-cased to the FITS-required E. Verified empirically that the output always carries a . or exponent (never misreads as integer), that e is the only lowercase letter emitted, and that all sampled values round-trip. Non-finite (inf/NaN) throws invalidValueForSerialization — the parser never yields those as .float (it demotes them to .unknown), so this path is genuinely unreachable for parsed values.

Tests (SwiftFITSTests/FITSValue.swift): per-case exact-literal assertions for logical/integer/float/string/undefined/unknown, a non-finite-throws test, and a valueRoundTrips test that renders every case and re-parses via FITSProperty asserting value equality.

Verification: xcodebuild test → TEST SUCCEEDED; swift test → 168 tests passed (+8). No regressions (purely additive).

Automated review loop: 1 round; converged with no Critical/High/Medium findings.

M3 Render FITSProperty to an 80-byte card Completed

Completed: 2026-07-11

Goal
Produce standards-compliant 80-byte cards from a property — the inverse of FITSProperty's parser, including long-string continuation.
Tasks
  • Implement card serialization: keyword left-justified in the 8-byte field, the =  value indicator, value literal via M2 with correct fixed-format column placement, optional / comment, blank-padded to exactly 80 bytes.
  • Handle commentary keywords (COMMENT, HISTORY, blank) and the CONTINUE long-string convention — the inverse of FITSProperty.merge(with:) — splitting values that exceed one card.
  • Validate keyword characters against CharacterSet.fitsKeyword on write; error (or coerce, per options) on invalid keywords.
  • Unit tests in SwiftFITSTests/FITSProperty.swift: single cards, commentary cards, and multi-card continuation; parse→render→parse equality, and byte-identity against known-good cards from TestUtilities.
Implementation notes

Implemented with TDD (red → green). Added public func serialized( options: ) throws -> [ String ] to FITSProperty (one or more exactly-80-char cards) plus internal static normalizedKeyword and several private render helpers. No new files.

Grounded in the FITS 4.0 standard (§4.2) and cross-checked against real fixtures: confirmed real files use fixed-format (values right-justified to byte 30, then / comment), unlike TestUtilities's looser free-format.

Layout (approved by the user before coding): keyword in bytes 1–8; = in 9–10; logical/integer/float right-justified to byte 30 (a 20-char field via the new FITSFile.fixedValueFieldWidth), values >20 chars falling back to free-format at byte 11; strings open-quote at byte 11 with interior quotes doubled (delegated to M2); comment as / <comment>; padded to 80. XTENSION value padded to 8 chars (FITS 4.0 §4.2.1) by padding the value before handing it to M2. Commentary emits one card per \n-line; long strings split into CONTINUE records (trailing & flag).

Keyword validation (user-approved): strict throws on an out-of-charset name; lenient (the new FITSSerializationOptions.coerceInvalidKeywords flag) upper-cases then re-validates length and charset; a name >8 chars throws in both modes. The coercion/rejection branches can only be exercised end-to-end once a property can be built with an arbitrary keyword (M6); until then they are tested directly via normalizedKeyword.

M4 Assemble a FITSSection into blocks with dirty-tracking Completed

Completed: 2026-07-11

Goal
Render a whole section to 2880-byte blocks from its model, while keeping clean sections byte-for-byte identical to their retained bytes. This is where "preserve untouched, re-render touched" is realized.
Tasks
  • Add a per-section needsSerialization (dirty) flag; reconcile it with the existing isFinalized lock so a section can be re-opened for rendering.
  • Implement header rendering: serialize all properties to cards (M3), append the END card, blank-pad to a whole number of 2880-byte blocks.
  • Implement data-section rendering: emit the data payload and zero/blank-pad to the 2880 boundary per the FITS standard.
  • Route data/appendData(to:): return retained blocks when clean, render from the model when dirty. Clean-path bytes must be unchanged.
  • Tests in SwiftFITSTests/FITSSection.swift: a clean parsed section re-serializes byte-identically; a synthetically built/dirtied section renders correct blocks and re-parses equal.
Implementation notes

Implemented with TDD (red → green). No new files (changes to FITSSection, FITSFile, and their tests).

Key design decision — throwing byte accessor (discussed with the user before coding). The plan says "route data/appendData(to:)", but rendering can throw (invalid keyword, non-finite float, over-long record from M2/M3), and a lazy dirty flag means the current bytes are only produced at serialize time. Keeping a non-throwing data would return stale bytes after a mutation. The user chose to make the byte accessor throwing so it is never stale:

  • FITSSection.serializedData(options:) throws -> Data — the router: clean → retained blocks (byte-for-byte), dirty → render from the model. Plus appendSerializedData(to:options:) throws as the aggregation primitive.
  • var data: Data { get throws } on both FITSSection and FITSFile — a convenience equal to serializedData(options: .strict). FITSFile.data changed from non-throwing to get throws; existing reads gained try (incl. allTestFilesRoundTrip). (This pulls the section-level serializedData forward from M5; M5 still adds the file-level serializedData(options:) + write + validation.)

Dirty-tracking: a private needsSerialization flag (default false), independent of isFinalized (a section can be finalized and dirty). markNeedsSerialization() is the internal hook M7's mutations will call. Parsing never sets it, so clean sections always re-emit retained bytes — allTestFilesRoundTrip stays byte-identical. (finalize now reads a new non-throwing retainedBytes instead of data, equivalent for a clean section.)

Rendering (grounded in FITS 4.0 §3.3.1/§3.3.2): a header/extension renders its properties to cards (M3) + the END card, space-padded to a whole 2880-byte block; a data section zero-pads its payload to the boundary. A minimal internal init(dataPayload:) builds a synthetic dirty data section (M7/M8 foundation, and enables the data-render test).

Verification: xcodebuild test → TEST SUCCEEDED; swift test → 183 tests passed (+3). Regression allTestFilesRoundTrip holds (clean path byte-identical).

M5 FITSFile write entry point & on-write validation Completed

Completed: 2026-07-11

Goal
Expose a public serialization/write API that emits a complete file and validates it against the FITS 4.0 standard, completing the "serialize an existing parsed file" capability.
Tasks
  • Add func serializedData(options: FITSSerializationOptions) throws -> Data and func write(to url: URL, options:) throws on FITSFile, aggregating sections via M4 (extending the existing data path).
  • On write (strict), validate mandatory keywords, BITPIX/NAXIS geometry, data-size consistency (reuse validateMandatoryKeywords / expectedDataSize / maxDataSize), and section ordering (primary HDU first). Lenient relaxes as appropriate.
  • Round-trip test across all fixtures: parse → serializedData → byte-equal to the original (clean path), and parse → write(to:) → re-read → equal.
  • Update the Xcode project; run the full suite via xcodebuild.
Implementation notes

Implemented with TDD (red → green). No new files (changes to FITSFile, FITSSection, FITSSerializationOptions, and their tests), so no Xcode-project changes.

Empirical grounding for the validation/round-trip interaction: before designing, ran a diagnostic parsing every fixture under .strict — only 2 of 14 fail, and both on property-value formatting (trailing quote junk; an unknown-typed value), not structure. So on-write structural validation (mandatory keywords, geometry, data-size, ordering) passes all 14 fixtures, which let data validate strictly without breaking the round-trip.

API: FITSFile.serializedData(options:) throws -> Data = validate then aggregate every section's bytes (via M4's appendSerializedData); write(to:options:) throws = serializedData + atomic disk write (replacing any existing file), mapping a write failure to FITSError.cannotWriteFile. data { get throws } was redefined to serializedData(options: .strict), so it now validates strictly too.

Validation (validateForSerialization, reusing the existing validateMandatoryKeywords / expectedDataSize): walks the sections as header/extension units each optionally followed by one data segment — the first section must be the primary header; every header/extension carries well-formed mandatory keywords; each data segment's size matches the geometry (via a new FITSSection.serializedByteCount, correct for clean and synthetic-data sections alike). Strict enforces all of it; lenient relaxes only the data-size check, via the new FITSSerializationOptions.allowDataSizeMismatch flag (the write-side counterpart to the parser's allowDataLengthMismatch). Mandatory-keyword and ordering checks are never relaxed.

Tests: a serializedData(.lenient) round-trip across all fixtures; a write → re-read → re-parse round-trip; strict-rejects/lenient-tolerates a data-size mismatch; and write to an unwritable path → cannotWriteFile. The existing allTestFilesRoundTrip (now try file.data = strict) still passes, confirming strict validation accepts every fixture.

Verification: xcodebuild test → TEST SUCCEEDED; swift test → 188 tests passed (+5). This completes Phase 1 (serialize an existing parsed file).

M6 Mutable & constructible FITSProperty Completed

Completed: 2026-07-11

Goal
Let consumers create and edit individual header records, the building block for both construction and modification.
Tasks
  • Add public initializers to build a property from keyword + FITSValue + optional comment (and convenience overloads for common value types), with keyword validation.
  • Make value and comment settable (or provide mutating methods) while keeping the parsed model consistent.
  • Unit tests: construct properties of each value kind, edit them, and serialize (M3) to correct cards.
Implementation notes

Implemented with TDD (red → green). Wrote the seven new tests first, confirmed the red state via xcodebuild (missing initializers/setters fail to compile), then implemented. No new files, so no Xcode-project changes.

Three design decisions were surfaced to the user and approved before coding:

  • Convenience initializers use distinct argument labels (logical:, integer:, float:, string:) rather than an overloaded value: — self-documenting and unambiguous at the call site.
  • The keyword name stays immutable (public private( set )): only value and comment become settable. Renaming a record is structural; to use a different keyword, build a new property. Documented on the name property.
  • Keyword validation reuses normalizedKeyword(_:options:) and takes a FITSSerializationOptions parameter, so .lenient/.coerceInvalidKeywords can upper-case an otherwise-valid keyword while .strict rejects it. The parameter defaults to .strict so the common convenience call stays ergonomic (FITSProperty( name: "SIMPLE", logical: true )); this default is flagged for review.

API: a public designated init( name:value:comment:options: ) throws (comment defaults to nil, options to .strict) plus four public convenience initializers delegating to it. Validation delegates to the existing M3 normalizedKeyword, so an out-of-charset or over-length name throws cannotSerialize; the blank keyword and the commentary keywords (COMMENT/HISTORY) are accepted. Consistent with the M2 design, a non-finite .float is accepted at construction and only rejected on serialization.

Mutability: value and comment changed from public private( set ) var to public var; both doc comments updated to describe in-place editing (and, for comment, the commentary newline-per-card behavior). No derived state at the property level, so plain setters keep the model consistent; the section-level dirty-tracking hook is M7's concern.

Appendix

Current model (read path) — the writer inverts each layer

FITSFile            .data  ── concatenates ──▶ full file bytes (byte-for-byte)
  └─ [FITSSection]  .appendData(to:) / .data  ── retained blocks today
       ├─ properties: [FITSProperty]   (headers only; END excluded but retained)
       │    └─ value: FITSValue        (logical | integer | float | string
       │                                | undefined | unknown)
       └─ blocks: [FITSBlock]          (private; raw 2880-byte originals)

Serialization layers added by this plan (bottom-up)

M2  FITSValue     ──▶ card literal            (inverse of value parser)
M3  FITSProperty  ──▶ 80-byte card(s)         (inverse of card parser + CONTINUE)
M4  FITSSection   ──▶ 2880-byte blocks        (+ END, padding, dirty-tracking)
M5  FITSFile      ──▶ Data / write(to:)       (+ standard validation)

Fidelity rule

A section renders from its model only when needsSerialization is set; otherwise it re-emits its retained blocks unchanged. This keeps unmodified files byte-for-byte identical (guarded by allTestFilesRoundTrip) while modified sections are regenerated to a standards-compliant form.
